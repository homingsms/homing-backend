# Homing API contracts

`@homing/contracts` holds the two API contracts of Homing Cloud and the TypeScript types generated from them.

| File | What it is |
| --- | --- |
| `openapi/public.yaml` | Public API for customer apps and the web console, plus webhook payloads (OpenAPI 3.1) |
| `openapi/device.yaml` | Phone to cloud protocol (OpenAPI 3.1) |
| `WEBHOOKS.md` | Webhook events, envelope, signature and retries |
| `src/generated/*.ts` | Types generated by `openapi-typescript`. Never edit by hand |
| `src/index.ts` | Named type aliases and constants (scopes, states, event types, header names) |

**Source of truth: the OpenAPI YAML.** Types are generated from it with `pnpm --filter @homing/contracts generate`, and `check:generated` fails when the committed types are stale. The server's e2e tests validate real responses against the schemas in `public.yaml` and `device.yaml`, and a unit test checks that the constants in `src/index.ts` match the spec enums. The server serves `public.yaml` read-only at `GET /api/v1/docs` (YAML) and `GET /api/v1/docs/openapi.json`.

The package exports TypeScript source (`exports["."] = ./src/index.ts`). Next.js consumers add it to `transpilePackages`; type-only imports need nothing extra.

## Public API, `/api/v1`

| Area | Operations |
| --- | --- |
| Auth | `POST /auth/sign-up` (optionally with `inviteToken`), `POST /auth/sign-in`, `POST /auth/sign-out`, `POST /auth/switch-account`, `GET /auth/me` |
| Account | `GET /account`, `PATCH /account` (name, routing strategy), `POST /account/deletion` |
| Team | `GET /team/members`, `PATCH/DELETE /team/members/{userId}`, `GET/POST /team/invites`, `DELETE /team/invites/{inviteId}`, `GET /invites/{token}`, `POST /invites/{token}/accept` |
| API keys | `GET /api-keys`, `POST /api-keys` (secret returned once), `DELETE /api-keys/{id}` (revoke) |
| Devices | `GET /devices`, `GET/PATCH/DELETE /devices/{id}`, `POST /devices/pairing-codes` |
| Messages | `POST /messages`, `GET /messages`, `GET /messages/{id}`, `POST /messages/{id}/cancel` |
| Inbox | `GET /inbox`, `GET /inbox/{id}`, `GET /inbox/{id}/attachments/{attachmentId}` |
| Webhooks | `GET/POST /webhooks`, `GET/PATCH/DELETE /webhooks/{id}`, `POST /webhooks/{id}/rotate-secret`, `POST /webhooks/{id}/test`, `GET /webhooks/{id}/deliveries`, `POST /webhooks/{id}/deliveries/{deliveryId}/redeliver` |
| Usage | `GET /usage/summary`, `GET /usage/daily`, `GET /usage/devices` |
| Health | `GET /health` |

**Auth.** The console signs in and gets an httpOnly `homing_session` cookie (`SameSite=Lax`, `Secure` in production). Applications send `Authorization: Bearer hk_live_...`. Keys carry scopes: `messages:send`, `messages:read`, `inbox:read`, `webhooks:manage`, `devices:manage`, `admin` (`admin` implies all). Managing API keys and the account needs a session or `admin`. Keys are stored as a peppered SHA-256 hash; only a short prefix is kept for display.

**Accounts, members and roles.** A user can belong to several accounts. A session acts in one account at a time: sign in opens the account the user used last, `POST /auth/switch-account` moves the session, and `GET /auth/me` lists every membership. Each membership has a role. Roles apply to sessions; API keys keep using scopes.

| Action | member | admin | owner |
| --- | --- | --- | --- |
| Send and cancel messages, read messages, inbox, devices, webhooks, usage, API key list, member list | yes | yes | yes |
| Change account settings; create or revoke API keys; create, change, test or delete webhooks; pair, change or remove devices | no | yes | yes |
| List, create and revoke invites; change roles and remove members other than owners | no | yes | yes |
| Grant or remove `owner`, change an owner's role, delete the account | no | no | yes |

Anyone can leave an account with `DELETE /team/members/{their id}`. An account always keeps at least one owner (`409` otherwise). Removing someone ends their sessions in that account at once; a user left with no account is deleted.

**Invites.** `POST /team/invites` takes an email and `admin` or `member` and returns `inviteUrl` (`<console>/invite/hi_...`) once; nothing is emailed. The token is stored as a hash, works once and expires after 7 days. Inviting the same email again revokes the earlier link. `GET /invites/{token}` is public so the console can show the account and inviter. The person joins either by signing up with `inviteToken` or, when already signed in, with `POST /invites/{token}/accept`. Both need the invited email; another address gets `403`.

**Account deletion.** `POST /account/deletion` with `{ accountName }` (the exact name), owner only, from a session. API keys are revoked, device tokens stop working, open invites are revoked and every session in the account ends, all in one transaction, and the response clears the cookie. The account's data is then deleted in the background; the maintenance sweep finishes any purge that was interrupted. Users who belong to no other account are removed.

**Messages.** One message has one recipient. `type` selects the body: `sms` (`text`), `data` (base64 `data`, `port`) or `mms` (`subject`, `text`, base64 `attachments`). Options: `idempotencyKey`, `deviceId`, `simSlot` (needs `deviceId`), `scheduleAt`, `validUntil`, `priority` (`normal` or `otp`), `deliveryReport`, `metadata`.

- Idempotency: the same key and body returns the original message with `200` and `Idempotent-Replayed: true`; the same key with a different body is `409`. Keys are unique per account and never expire.
- Routing: explicit `deviceId` pins the message. Otherwise the account's strategy (`round_robin` or `least_used`) picks an online, unpaused device under its daily limit, and the cloud picks the SIM when the device pulls. Messages with no eligible device wait as `pending` and go to the first eligible device that pulls.
- Daily limits per device and per SIM count messages leased in the current UTC day.
- `otp` messages are leased before `normal` ones and wake the phone with a high priority push.
- States: `scheduled` then `pending` then `leased` (pulled by a device) then `queued` (in the phone's send queue) then `sending`, `sent`, `delivered`. `failed`, `cancelled`, `expired` and `delivered` are final. Forward jumps are allowed (a device may report `sent` right after `leased`); going back is not. `sent` may still become `failed` when the carrier reports a delivery failure. Cancel works in `scheduled`, `pending` and `leased`. `GET /messages/{id}` returns the timeline in `events`.
- An expired lease puts the message back to `pending` (up to 3 attempts, then `failed` with code `lease_expired`). A `pending` message past `validUntil` becomes `expired`.

**Devices.** `status` is `offline` after missed heartbeats, as before. A heartbeating device is `online` when nothing limits it and `degraded` when `statusReasons` lists a problem: `paused`, `low_battery` (below 15% and not charging), `no_network`, `all_sims_disabled`, `sim_no_signal` (with `simSlot`), `device_cap_reached`, `sim_cap_reached` (with `simSlot`) or `stale_heartbeat` (no heartbeat for two intervals). A degraded device is still connected and can still be picked when it has capacity. Offline devices only list setting and cap reasons. Presence webhooks (`device.online`, `device.offline`) and the usage counters still report presence only.

**Lists** use opaque cursors: `?cursor=<nextCursor>&limit=1..100`, newest first, `nextCursor: null` on the last page.

**Errors** always use `{ statusCode, message, error, timestamp, path }`. Validation errors put a list of strings in `message`. `429` carries `Retry-After`.

## Device protocol, `/api/v1/device`

| Operation | Purpose |
| --- | --- |
| `POST /device/pair` | Trade a single-use pairing code (10 minutes) for a device token `hd_...` and initial settings |
| `POST /device/heartbeat` | Battery, charging, network, per-SIM carrier, signal and sent today, app version. Returns `pendingMessages` and `settingsVersion` |
| `PUT /device/fcm-token` | Replace or clear the FCM token |
| `POST /device/messages/pull` | Lease up to 50 messages. Each carries `simSlot`, `attempt` and `leaseExpiresAt` |
| `POST /device/messages/states` | Batch of state reports (`queued`, `sending`, `sent`, `delivered`, `failed` with an error code). Per-item result `accepted`, `duplicate` or `rejected` with a reason |
| `POST /device/inbox` | Batch of received SMS, data SMS and MMS with base64 attachments. `localId` makes retries safe |
| `GET /device/settings` | Remote settings: pause, limits, intervals, lease length, opt-out keywords |

**Leasing.** Pull selects messages with `FOR UPDATE SKIP LOCKED` inside one transaction, so two phones can never lease the same message. A lease lasts `leaseSeconds` (default 120) and is confirmed by reporting `queued`. Reports from a device that does not hold the message are rejected with `not_leased_to_device`. A late report from the device whose lease just expired is still accepted while the message waits as `pending`, so a slow phone that did send the message does not cause a second send.

**Wake-up.** When a message is routed to a device the cloud sends an FCM data message `{ kind: "homing.wake", reason, deviceId, sentAt }` with `reason` `messages_pending`, `settings_changed` or `device_removed`. All values are strings. The push only wakes the phone; it never carries message content. Without FCM credentials the server skips pushes and the phone relies on its pull interval.

**Presence.** A device is `online` after a heartbeat and `offline` after missing three intervals (180 seconds by default). Both changes emit webhooks.

`GET /messages` filters by `state`, `type`, `deviceId`, `simSlot`, `to` and creation time.

## Webhooks

Nine subscribable events plus `webhook.test`, a JSON envelope `{ id, type, createdAt, accountId, data }`, and `Homing-Signature: t=<unix>,v1=<HMAC-SHA256 hex of "t.body">` with a 300 second replay window. Up to 8 attempts with exponential backoff from 60 seconds. Events are written to an outbox table in the same transaction as the change they describe, so a committed change always produces its event and a rolled back one never does. Targets are resolved once per attempt, checked against private ranges, and the connection goes to that checked address. Details in `WEBHOOKS.md`.

## Design choices

- One recipient per message keeps state, retries, idempotency and webhooks one-to-one. Bulk sends are many calls with their own idempotency keys.
- The cloud owns routing and SIM choice so that limits are enforced in one place; the phone may still fall back to its default SIM when `simSlot` is `null`.
- State names describe where the message is (`pending` in the cloud, `queued` on the phone), not what the server did to it.
- Prefixed IDs (`msg_`, `dev_`, `inb_`, `whk_`, `whd_`, `evt_`, `key_`, `usr_`, `acc_`) make logs and support easier.
- Secrets (API keys, device tokens, pairing codes, sessions) are stored only as hashes. Webhook signing secrets must be readable to sign, so they are encrypted at rest with AES-256-GCM.
- Snake case for enum values, camel case for fields, ISO 8601 UTC timestamps, base64 for binary inside JSON.

## Local mode on the phone

In local mode the Android app's built-in server should mirror these public operations with the same request and response shapes, under the same `/api/v1` prefix, authenticated with `Authorization: Bearer hk_live_...` keys created on the phone:

| Mirror | Notes |
| --- | --- |
| `POST /messages`, `GET /messages`, `GET /messages/{id}`, `POST /messages/{id}/cancel` | Same schemas. `deviceId` is ignored or must be the phone's own ID. `leased` never appears; local messages go straight from `pending` to `queued`. Cancel works until `queued` |
| `GET /inbox`, `GET /inbox/{id}`, `GET /inbox/{id}/attachments/{attachmentId}` | Same schemas. `deviceId` is the phone's own ID |
| `GET/POST /webhooks`, `GET/PATCH/DELETE /webhooks/{id}`, `POST /webhooks/{id}/test`, deliveries | Same events, envelope and signature scheme, so receivers work with both modes |
| `GET /health` | Same `status`, `version` and `time`. The phone may add its own checks beside or instead of `database` and `redis`; a shared schema for that is still open |

Scopes on the phone use the same names; `devices:manage` and `admin` cover the phone's own settings. Auth, account, API key management, device management, pairing and usage stay cloud only; the phone manages its own keys in the app UI.
